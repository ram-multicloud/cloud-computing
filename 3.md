# Scaling and Elasticity in Cloud Computing

## Overview

**Elasticity** is the capability to automatically adjust compute resources to match demand.

It covers two dimensions of change:

| Dimension | Direction | Meaning |
|---|---|---|
| Per-instance resources | Scale up / Scale down | More or fewer resources *within* a single instance |
| Instance count | Scale out / Scale in | More or fewer instances serving traffic |

**Why it matters** — effective elasticity improves:

- **Performance** — capacity grows before users feel the slowdown
- **Cost efficiency** — you stop paying for capacity you aren't using
- **Resilience** — load is spread across more (or healthier) resources

---

## Scaling Types

### 1. Vertical Scaling (Scale Up / Down)

**Definition:** Adjusting the resources of a *single* instance — CPU, RAM, or instance size/type.

| Term | Meaning |
|---|---|
| Scale up | Add more resources (e.g., `t3.medium` → `t3.xlarge`) |
| Scale down | Reduce resources |

**Key characteristics:**

- ⚠️ Typically incurs **downtime** — the instance must be stopped/resized or replaced.
- 🚧 Limited by the **largest available instance type** — you eventually hit a ceiling.

**Analogy:** Like replacing a small delivery van with a bigger truck — one vehicle, more capacity, but it has to go off the road while you swap it.

### 2. Horizontal Scaling (Scale Out / In)

**Definition:** Adjusting the *number* of instances serving traffic.

| Term | Meaning |
|---|---|
| Scale out | Add instances |
| Scale in | Remove instances |

**Key characteristics:**

- ✅ Can happen **without downtime** — when paired with a load balancer and health checks.
- 🎯 Best suited for **stateless** services, or services with externally managed state (e.g., session data in Redis, not on the instance itself).

**Analogy:** Like adding more delivery vans to the fleet instead of building a bigger one — trucks already on the road keep running while new ones join in.

---

## Vertical vs. Horizontal — Quick Comparison

| Aspect | Vertical Scaling | Horizontal Scaling |
|---|---|---|
| What changes | Size of one instance | Number of instances |
| Downtime | Usually yes | No, with LB + health checks |
| Ceiling | Limited by max instance size | Practically limitless |
| State handling | Simpler (single instance) | Needs stateless design or external state store |
| Typical tooling | Resize instance / change instance type | Auto Scaling Groups, load balancers |

## AWS Auto Scaling Groups

- Use **Auto Scaling Groups (ASG)** with Launch Templates or Launch Configurations referencing a pre-baked AMI.
- Attach to an **Application/Network Load Balancer** with health checks.
- Configure scaling policies:
  * Target tracking
  * Step scaling
  * Scheduled scaling
- Options for instance protection and draining.
