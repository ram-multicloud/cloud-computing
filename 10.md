# Azure Functions Hosting Plans

Azure Functions offers five hosting options, each trading off scaling behavior, cost model, and control over compute. Here's what each one means and when to use it.

## Comparison Table

| Feature | Flex Consumption | Functions Premium | App Service | Container Apps environment | Consumption (Windows) |
|---|---|---|---|---|---|
| **Scale to zero** | ✅ | ❌ | ❌ | ✅ | ✅ |
| **Scale behavior** | Fast event-driven | Event-driven | Metrics based | Event-driven with KEDA | Event-driven |
| **Virtual networking** | ✅ | ✅ | ✅ | ✅ | ❌ |
| **Dedicated compute / prevent cold start** | Optional (Always Ready) | Minimum 1 instance required | Minimum 1 instance required | Optional (minimum replicas) | ❌ |
| **Max scale out (instances)** | 1000 | 100 | 30 | 300 | 200 |

## What Each Plan Is For

### Flex Consumption
Pay-as-you-go billing combined with high scalability and virtual networking support. You can optionally reserve "Always Ready" instances to avoid cold starts while still scaling to zero when idle. Best default choice for most new function apps — highest max scale-out (1000 instances) with the flexibility of consumption pricing.

### Functions Premium
Lets you run multiple function apps on the same plan with event-driven scaling. Requires at least one warm instance running at all times (no scale-to-zero), which eliminates cold starts but means you're always paying for some baseline compute. Good fit when you need VNET integration and predictable performance but don't want full App Service management overhead.

### App Service
Runs function apps on the same underlying plan as web apps, scaling based on metrics (CPU, memory, etc.) rather than events. Requires a minimum of one instance. Makes sense when you already have an App Service Plan you want to share, or need more control over the underlying compute size.

### Container Apps Environment
Hosts function apps alongside other containerized microservices, using KEDA for event-driven scaling. Supports scale-to-zero and optional minimum replicas. The right choice if your functions are part of a broader containerized/microservices architecture.

### Consumption (Windows)
The classic pay-as-you-go model — you're billed only for the compute used while functions are actually running. Scales to zero and event-driven, but has no virtual networking support and no option for dedicated/always-warm instances, so cold starts are unavoidable. Simplest and cheapest for low-traffic or unpredictable workloads that don't need VNET integration.

## Quick Decision Guide

- **Need VNET + scale-to-zero + cheapest scaling model?** → Flex Consumption
- **Need to avoid cold starts entirely, running multiple apps together?** → Functions Premium
- **Already on App Service / need fine-grained compute control?** → App Service
- **Part of a containerized/microservices setup?** → Container Apps environment
- **Simple, low-traffic app, no networking requirements?** → Consumption (Windows)
