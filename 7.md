# AWS Auto Scaling

Auto Scaling automatically adds or removes EC2 instances in an **Auto Scaling Group (ASG)** to match demand — no manual intervention.

## How It Works

1. Define a **launch template** (AMI, instance type, key pair, security groups).
2. Create an **ASG** with min / max / desired capacity, using that template.
3. ASG launches instances across AZs per the distribution strategy.
4. **Health checks** detect and replace unhealthy instances.
5. **Scaling policies** add/remove instances based on metrics or schedule.
6. **Load balancer** (optional) spreads traffic across healthy instances.

## Prerequisites
- Launch template (AMI, instance type, key pair, security groups, IAM role, user data)
- VPC with subnets in target AZs
- (Optional) Load balancer + target group
- (Optional) SNS topic for notifications

## AZ Distribution

| Strategy | Behavior |
|---|---|
| **Balanced best effort** | Spreads evenly, but shifts to another AZ if one lacks capacity |
| **Balanced only** | Spreads strictly evenly; won't over-provision another AZ |
| **Reserve and balance** | Reserves capacity per AZ upfront, then balances (fits with Reserved Instances/Capacity Reservations) |

## Additional Capacity Settings

- **Capacity Rebalancing** — proactively replaces at-risk Spot Instances
- **Default Cooldown** — wait time between scaling actions
- **Default Instance Warmup** — time before a new instance counts toward scaling metrics
- **Mixed Instances Policy** — mix instance types / On-Demand + Spot

## Load Balancer

- **ALB** — Layer 7 (HTTP/HTTPS)
- **NLB** — Layer 4 (TCP/UDP, high throughput)
- **CLB** — legacy, avoid for new setups

ASG auto-registers/deregisters instances with the target group and can use ELB health checks.

## VPC Lattice Integration

Attach an ASG as a **target group** in a VPC Lattice service network — routes traffic to it from other services across VPCs/accounts without peering, Transit Gateway, or PrivateLink.

## Health Checks

- **EC2 status checks** — default, hardware/software level
- **ELB health checks** — app-level (e.g., HTTP 200), used if a load balancer is attached
- **Health check grace period** — time given before checks start counting

## Configure Group Size and Scaling (Optional)

- **Min / Max / Desired capacity**
- **Manual** — set desired capacity directly
- **Scheduled** — change capacity at set times
- **Dynamic**: Target tracking, Step scaling, Simple scaling
- **Predictive** — ML-based, scales ahead of forecasted demand

## Instance Maintenance Policy

Controls **min/max healthy percentage** during instance replacement — determines launch-first vs. terminate-first behavior, keeping availability during refreshes.

## Placement Group

- **Cluster** — same AZ, low latency (HPC)
- **Spread** — distinct hardware per instance (max 7/AZ)
- **Partition** — isolated hardware groups (e.g., Hadoop, Cassandra)

Strict placement (esp. Cluster) can limit launch capacity.

## Notifications

SNS topic on events: `EC2_INSTANCE_LAUNCH`, `LAUNCH_ERROR`, `TERMINATE`, `TERMINATE_ERROR`.

**Lifecycle Hooks** pause instances (`Pending:Wait` / `Terminating:Wait`) for custom actions before they go live or terminate.
